# Harbor — YeNo paper bot

A runnable Python submission candidate for the YeNo × Builderr Volume Bot Challenge.
The decision server uses only the Python 3.12 standard library. It cannot place real orders.

The current candidate was evaluated on 48 recorded five-minute markets and cross-checked on five
other markets. The [comparison report](results/harbor-revision.json) records cash, eligible volume
and completed cycles. Builderr evaluates qualification on its private 24-hour paper run.

## Run and test

From this directory:

```bash
python3 -m yeno.server
```

The evaluator calls `POST http://127.0.0.1:8080/decide`. In a second terminal:

```bash
python3 research/yeno-smoke-test.py --observation research/yeno-sample-observation.json
python3 -m unittest discover -v
python3 -m tools.validate
```

The first command is Builderr's unchanged smoke test. `tools.validate` also measures 600 local
HTTP responses across BUY, SELL and HOLD paths. `GET /health` reports readiness.
Set `YENO_HOST` and `YENO_PORT`, or pass `--host` and `--port`, when another process needs access.
Public hosting is optional; a repository with an immutable commit is an accepted submission format.

## Strategy

- Buy the BTC-reference favourite after the opening minute and with more than 22 seconds remaining, at asks from 0.94 to 0.969.
- Require a three-cent model edge using a 60-second settlement TWAP model and trailing BTC volatility.
- Use up to $5 including both fee layers, with sufficient shares after a two-cent adverse sizing stress.
- Reject entries whose intended 99-cent exit would already lose money after fees and L2 entry slippage.
- Exit at a 99-cent bid with adequate executable pricing, even after a bad entry fill, and start normal
  deadline exits at 20 seconds remaining. Entry cost must not trap capital in a missed break-even exit.
- Preserve SELL intent across partial fills. Sustained shallow depth can move the exit earlier;
  one fleeting thin quote cannot. After a depth-triggered deadline exit, do not re-enter that market.
- Estimate volatility from price changes between observed one-second closes and integrate the observed TWAP segment by time.
  Missing coverage, stale/future references, pending actions and non-finite inputs block entries.
- Stop buying once the evaluator's completed volume reaches its target. Never maintain a competing cash ledger.

The model remains a hypothesis: Brownian returns, a spot proxy for the settlement feed, and uncertain future
liquidity can all fail. The execution reserve defaults to zero; the two-cent sizing check is **not** protection
against two-cent P&L slippage. Configuration is frozen in `yeno/strategy.py`.

## Collect real data

The recorder alone requires `websockets==16.0` (`requirements-research.txt`). It reads public data,
without keys or a wallet. See [the verified sources and data limitations](research/DATA.md).

```bash
python3 -m tools.capture --windows 6 --max-mb 4096 --output data/new-capture
python3 -m tools.replay_capture data/new-capture --output results/real-capture.json
```

Use a new output directory for every capture. The default records the current partial window and the
next entire five-minute window; `--windows 6` records six full windows with rolling subscriptions, retaining
raw timestamps and events. Uncompressed and compressed size caps stop runaway recording. A short connection check is available
with `--seconds 30`. The normalizer excludes partial first/last windows and never backfills targets.
Read the recorder's manifest and replay diagnostics before interpreting any result.

For comparison with an independently obtained, locally reviewed reference implementation, pass
`--reference-dir /absolute/path/to/reference` to either replay command. That source is deliberately
not bundled or downloaded automatically.

## Replay contract and evidence

`python3 -m replay.cli --input recordings.jsonl --output results/replay.json` accepts receive-time ordered
rows with `timestamp`, `market`, `reference` and `books`. Each outcome book must include its own
`observedAt`, `minOrderSize`, `bids` and `asks`. Account and cash fields are generated by the replay ledger.
For explicit settlement, a row at/after close may include `resolvedOutcome`; settlements credit no volume.

The local ledger independently implements fees, 250 ms latency, outcome-specific later updates,
minimum BUY size, partial exits, one position and completed-cycle-only volume. It stops at the first
flat target crossing. It has **no official evaluator parity validation**. Dust tolerance and fee rounding
follow the public starter's conventions; production behavior can differ.

Synthetic regimes can exercise code paths:

```bash
python3 -m replay.cli --synthetic choppy --markets 288 --output results/software-stress.json
```

These are not market backtests. A synthetic `$1,000` crossing is not evidence of a tournament win.
Published results in `results/` retain their evidence class and source/input hashes.

## Submission

Builderr requests a bot name, contact, runnable repository or HTTPS endpoint, and an immutable commit or
container digest. Runtime command: `python3 -m yeno.server`. No external access is required by the bot.
See [the submission checklist](SUBMISSION.md) and [research notes](research/STRATEGY.md).
The repository is prepared for submission. No competition entry has been emailed or submitted.
The submitted immutable commit identifies the exact build to evaluate; do not use a moving branch
name as the frozen build identifier. Historical replay reports retain their original source hashes.
